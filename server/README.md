# Rakshak — server

Express API for Rakshak, an AI cybersecurity assistant.

## Getting started

```bash
npm install
cp .env.example .env
npm run dev
```

Server boots on `http://localhost:5000`. Verify it's alive:

```bash
curl http://localhost:5000/api/health
```

## Structure

```
config/      env loading, MongoDB connection (config/db.js)
controllers/ thin request handlers — parse req, call services, shape res
routes/      route tables, one file per resource, aggregated in routes/index.js
middleware/  errorHandler, notFound, (later) auth, validation
models/      Mongoose schemas — User, Chat, UploadedLog, Threat, IncidentReport
services/    business logic — ai/, logParser/, threatIntel/, reportGenerator/
utils/       logger, asyncHandler, ApiError
uploads/     multer upload destination (gitignored)
app.js       Express app config — middleware + routes, no listen()
server.js    boot entry point — connects to MongoDB, then calls app.listen()
```

`app.js` and `server.js` are split on purpose: `app.js` can be imported directly
by integration tests (e.g. supertest) without binding a real port.

## MongoDB (Atlas)

1. Create a free cluster at https://www.mongodb.com/cloud/atlas
2. Database Access → add a database user (username + password)
3. Network Access → add your current IP (or `0.0.0.0/0` for local dev only)
4. Database → Connect → Drivers → copy the Node.js connection string
5. Paste it into `.env` as `MONGO_URI`, replacing `<password>` with your actual password

The server refuses to start if MongoDB is unreachable — `npm run dev` will
exit with a clear error instead of silently accepting requests it can't serve.
`GET /api/health` also reports live connection state (`database: "connected"`).


## Auth (Step 5)

```
POST /api/auth/signup   { name, email, password }  -> 201 { user, token }
POST /api/auth/login    { email, password }         -> 200 { user, token }
GET  /api/auth/me       Authorization: Bearer <token> -> 200 { user }
```

- Passwords hashed with bcrypt (12 salt rounds), never returned in any response.
- JWT signed with `JWT_SECRET` (server refuses to boot without it set), default 7-day expiry.
- `/auth/signup` and `/auth/login` are rate-limited separately from the rest of the API (20 attempts / 15 min per IP) to slow down credential stuffing.
- `protect` middleware re-fetches the user on every request rather than trusting the token payload alone, so a deleted account can't keep using a still-valid token.

## Dashboard (Step 6)

```
GET /api/dashboard/stats   Authorization: Bearer <token>
  -> { totals: { logs, reports, threats, conversations },
       severityDistribution: { low, medium, high, critical },
       recentConversations: [{ id, title, updatedAt }] }
```

All counts scoped to `req.user._id` — one user never sees another's data.
Runs the four count queries and the severity aggregation concurrently via
`Promise.all` rather than sequentially awaiting each one.

## Chat (Step 7 — UI + storage, AI reply is a placeholder until Step 8)

```
GET    /api/chat                 -> list conversations (title, timestamps)
POST   /api/chat                 -> create a new empty conversation
GET    /api/chat/:id             -> full conversation incl. messages
DELETE /api/chat/:id             -> delete a conversation
POST   /api/chat/:id/messages    { content } -> append user message, get AI reply, both saved
```

All routes require auth and are scoped to `req.user`. The AI reply is
currently generated by `services/ai/aiProvider.js`, a placeholder that
returns a canned string — `chatService.appendUserMessage` calls it exactly
the way it'll call the real Ollama/OpenAI integration once Step 8 replaces
that one file. Nothing else changes.

## AI integration (Step 8)

`AI_PROVIDER=ollama` (default) or `AI_PROVIDER=openai` in `.env` — no code
changes needed to switch. Both providers share one interface
(`services/ai/aiProvider.js`), so `chatService.js` never knows or cares
which one is active.

**Ollama (default, free, local):**
```bash
# separately, install Ollama: https://ollama.com/download
ollama pull llama3.2
ollama serve          # runs on http://localhost:11434 by default
```

**OpenAI (cloud, paid):** set `AI_PROVIDER=openai` and `OPENAI_API_KEY` in `.env`.

Both providers throw a clear `502`/`500` error (with an actionable message,
e.g. "Is ollama serve running?") rather than letting a raw connection error
or bad API key leak to the client.
